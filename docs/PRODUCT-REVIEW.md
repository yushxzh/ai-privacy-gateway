# 产品问题梳理与下一轮验收

> 历史问题记录。当前需求、实现状态与优先级统一维护在 [全局 PRD](PRD.md)；一键接入和规则管理的最新范围见 [MVP 功能表](MVP.md)。

> 本文保留当时的分析快照。0.1.5 已完成默认替换、逐规则动作 / 启停、自定义规则、本地保存和部分页面精简；最新事实与剩余缺口见 [0.1.5 交付与验证](ITERATION-0.1.5.md)。历史建议中的「凭据默认阻断」已按用户要求调整。

日期：2026-09-12。依据：用户截图、WorkBuddy 5.5.2 与 App 的实际界面、当前 0.1.4 源码及本轮原生请求复测。

**主要问题是接入流程和功能组织没有围绕真实使用完成闭环。** 页面展示了很多说明与开发验证，却没有明确回答「当前客户端是否真的受保护」，也缺少用户可管理的规则。

本轮已修正本机 WorkBuddy 的连接配置，并补充[使用指南](USAGE.md)。下文界面精简、自定义规则和语义分类均为改造方案，尚未修改应用代码。既有测试通过不代表这些缺失功能已经完成。

## 1. 为什么这次设置后没有生效

| 证据 | 判断 |
| --- | --- |
| 用户 13:50 截图中，WorkBuddy 回复仍包含合成邮箱和手机号 | 需要检查真实外发内容，不能只凭回复判断过滤状态 |
| 现场检查时 WorkBuddy 为「直接连接」，网关记录为零 | WorkBuddy 没有经过网关；这是本次未生效的直接原因 |
| App 已显示「网关运行中」和原生 HTTPS 启动提示 | 该提示只反映本地代理进程运行，未验证客户端接入与证书信任，容易误导 |
| 完成当前证书信任、重开 WorkBuddy、开启手动代理后，14:04 产生两条替换记录 | 原登录和 Auto 模型路径可以完成这类文本过滤，无需更换供应商或另填 API Key |
| 14:04:16 的记录详情显示正文已校验、原认证保持不变、命中原文已移除、官方服务返回成功 | 本轮效果有实际发送正文证据，超出了演示或界面预览的验证范围 |

当前 `src/main/index.ts` 的 `nativeHttps` 状态来自 `nativeProxy.running`。启停按钮只管理网关进程；证书信任、WorkBuddy 代理设置、客户端重启和恢复都没有纳入统一流程。

普通 App 启动还缺少原生入口所需的实验运行时参数。可重复使用的产品不能依赖用户知道这些实现细节，也不能让用户把「服务启动」当作「保护已生效」。

## 2. 对四个问题的处理意见

| 问题 | 当前事实 | 改造要求 |
| --- | --- | --- |
| 凭据检测展示过多 Demo | 规则页以正反例、自定义测试输入和整组样例验证为核心，没有规则增删改 | 内置样例和批量验证移出日常界面，保留在测试与开发文档中。规则页改为可操作的规则列表；仅在编辑自定义规则时保留按需测试 |
| 很多页面只是说明文档 | 多个平台标签只有适配条件、实验说明或官方文档链接；原生 HTTPS 横幅没有接入动作 | 长说明、适配研究和实验细节放仓库。主界面只展示可用客户端、当前状态、下一步动作与必要错误信息；未适配平台不以可操作的接入入口出现 |
| 工作空间 / LOCAL 多余 | 当前只支持单一本地环境，没有空间切换、租户或远程空间 | 删除「工作空间」「LOCAL」「个人空间」「本地模式」的重复装饰。保留一处实际存储行为说明即可 |
| 语义分类与规则管理缺失 | 语义分类是关闭的空实现；已有 14 条内置规则，没有用户规则管理 | 把「内置规则 + 自定义规则」做成真实功能。语义分类保留为明确待办，完成前移除日常导航中的占位入口 |

这次清理应保留已经有价值的真实记录、原文对比、筛选和启停能力。目标是减少操作负担，补齐规则和接入动作，不是简单删除所有按钮。

## 3. 页面与按钮核查

核查方式：现场操作证明连接状态与真实记录；下表其他动作结合已查看的页面、处理函数与既有测试进行检查。本轮没有逐一执行会改变模型配置、清空记录或发起额外收费请求的操作，也没有把源码存在当成完整流程验收。

| 页面 / 操作 | 目前真正做的事 | 用户使用中的缺口 | 处理方向 |
| --- | --- | --- | --- |
| 工作台「运行本地演示」 | 生成演示请求，已有处理函数 | 占据主操作位置，不能启用 WorkBuddy 原生保护 | 从日常首页移除，开发样例留仓库 |
| 工作台复制本地地址 | 复制普通 API 地址 `8787/v1` | 原生 WorkBuddy 要设置网络代理 `18788`，复制此地址无法接入 | 接入流程按客户端提供正确动作，不混用两类地址 |
| 请求筛选、搜索、打开详情、显示原文 | 操作真实记录 | 这些功能有用；记录不应被演示数据淹没 | 保留，优先显示来源、时间、命中规则、动作与是否实际发送 |
| 「清空记录」 | 清空当前内存记录；无记录时禁用 | 禁用状态本身合理，不能归为无效按钮 | 保留在记录页次要位置 |
| WorkBuddy「重新检查配置」 | 读取已保存的自定义模型 | 无法检查 Auto 模型的代理是否启用 | 作为高级 API 配置操作；新增真正的原生接入检查 |
| WorkBuddy 每个自定义模型的「启用过滤 / 恢复直连」 | 修改或恢复该模型 API 连接 | 仅适用于自定义供应商，不能代表原登录保护 | 保留到高级自定义 API 入口，并明确作用对象 |
| Codex / Claude「启用原认证转发」 | 切换网关的转发模式 | 客户端仍需执行配置命令；真实完整任务未验收 | 不标作一键接入，完成真实验证后再进入主要客户端列表 |
| 多平台标签和「官方文档」 | 切换说明或打开外部文档 | 有响应，但不完成用户想要的接入 | 待适配清单与研究移至仓库 |
| 规则页「运行验证 / 验证本组全部样例」 | 调用本地检测器；不保存规则 | 「自定义内容」只是测试文本，不是新增检测规则 | 移走样例库与批量测试；补充真正的规则编辑和保存 |
| 「语义分类 · 预留」 | 静态展示，没有功能 | 占位看起来像已有能力 | 未实现前不占用日常功能入口 |
| 设置中的启动 / 停止、应用设置 | 管理网关进程及普通 API 设置 | 不安装信任、不配置 WorkBuddy、不恢复它的网络 | 接入与断开组成完整流程，普通 API 配置收进高级设置 |

界面整理参考 Impeccable 4.0.4 的精简流程；本次是功能与信息结构梳理，未进行正式双评审打分，也未声称新的界面已经实现。

## 4. 建议收敛到四个入口

| 入口 | 用户要完成的事 | 保留的主要内容 |
| --- | --- | --- |
| 保护 | 让原来的应用真正经过本地过滤 | 已支持客户端、开启 / 停止保护、连接检查、最近检查时间、必要的修复动作 |
| 记录 | 知道哪条真实请求经过了什么处理 | 请求列表、来源、命中规则、替换对比、阻断原因、实际发送状态 |
| 规则 | 决定检查哪些内容、命中后怎么办 | 内置与自定义规则、启停、增删改、处理动作；编辑时按需测试 |
| 设置 | 调整应用运行方式 | 生命周期、存储行为、版本、帮助链接；自定义 API 与技术参数放高级区域 |

主页的核心状态应区分：

| 状态 | 允许表达的事实 | 对应动作 |
| --- | --- | --- |
| 未接入 | 客户端尚未配置 | 「开启保护」 |
| 需要授权 / 重启 | 有具体步骤未完成 | 「完成授权」或「重启应用」 |
| 已接入，等待首个请求 | 配置和本地连接检查通过，尚无真实请求证据 | 简短提示在客户端正常使用 |
| 最近请求已检查 | 有来源、时间和检测结果支持 | 查看最近记录 |
| 连接异常 / 部分请求未覆盖 | 有明确失败或能力边界 | 显示原因和可执行的恢复动作 |
| 已停止 | 客户端原连接已经恢复 | 「开启保护」 |

「最近请求已检查」不能缩写成「所有内容安全」。未识别协议、未知域名与未实现的检测能力仍要按事实呈现。

## 5. 一键生效需要交付什么

一键生效目前没有实现。本轮通过使用文档提供可重复操作的路径；下一轮应把已验证的步骤整合进 App。

### 开启保护

1. 发现客户端和适用版本，检查本地端口与运行时。
2. 准备本机证书，检查信任是否完整；确需系统授权时展示系统确认。
3. 读取并备份客户端原代理配置，应用该客户端支持的代理设置。
4. 判断是否需要客户端重启，先处理正在运行的任务与未发送输入，再完成重启。
5. 验证本地连接，显示「已接入，等待首个请求」。连接检查不应偷偷向模型发送收费测试。
6. 第一条真实请求完成后，更新最近检查时间与实际处理结果。

### 停止与异常恢复

先恢复客户端原配置，再停止网关。原来使用其他代理的用户应恢复到原代理，不能统一改成直连；如果用户在接入后自行改过配置，应比较当前值再处理，避免覆盖新设置。

关闭 App、正常重启、启动失败和代理崩溃都要有恢复路径。普通暂停保留可复用的证书；完全卸载时再移除本产品安装的对应信任与私钥。异常恢复还未实现时，必须保留简短的手动恢复步骤。

当前采用显式代理，需要客户端设置 HTTP 代理和证书信任，这是两个独立步骤。mitmproxy 的[代理模式说明](https://docs.mitmproxy.org/stable/concepts/modes/)也分别说明了这两项要求。后续可以比较其他接入方式，但不能把某个代理工具支持本地捕获等同于本项目已经完成一键接入。

## 6. 内置规则与自定义规则怎么做

### 先纠正当前能力描述

现有规则全部随程序内置，不是用户自行添加的。当前有 **10 条凭据规则 + 4 条个人信息规则**。

| 类别 | 当前覆盖 |
| --- | --- |
| 凭据 | 私钥块、明确私钥字段、API Key、云服务密钥、带密码连接地址、密码、OAuth Token、JWT / JWE、BIP39 助记词、明确标注的助记词 |
| 个人信息 | 邮箱、中国大陆手机号、身份证格式、明确账号字段 |

现有检测已包含通用字段规则，例如 `api_key`、`client_secret`、`password`、`access_token` 等字段后的值；同时包含常见厂商前缀和 BIP39 字典校验。问题是这些匹配方式与动作写在代码里，用户不能新增、修改或禁用。

不能用一条通用正则可靠判断所有没有标注的随机字符串是否为密钥。合理的组合是：

- 内置明确格式与校验，例如私钥块、厂商令牌前缀、助记词校验。
- 内置上下文字段规则，例如带赋值的密钥、密码和令牌字段。
- 用户补充业务关键词、专属格式或正则，并选择替换或阻断。

这种「默认规则 + 自定义扩展」已有实际扫描器采用，例如 [Gitleaks 配置](https://github.com/gitleaks/gitleaks#configuration)。本方案只参考其配置分工，不在本轮引入该依赖。

### 最小规则管理

| 属性 / 操作 | 要求 |
| --- | --- |
| 名称与来源 | 区分「内置」「自定义」；记录能反查命中的规则 |
| 匹配方式 | 内置规则保留现有格式与算法；自定义首版提供关键词 / 固定文本、正则 |
| 分类与动作 | 凭据默认阻断、个人信息默认替换；自定义规则明确选择替换或阻断 |
| 启用状态 | 规则可启停，关闭后对下一条请求生效 |
| 增删改 | 可新建、编辑、删除自定义规则；内置规则的默认定义由程序维护 |
| 本地保存 | 自定义规则和对内置规则的覆盖设置分开保存，重启后保留；应用升级不覆盖用户配置 |
| 按需测试 | 编辑器可输入一段文本验证匹配和动作；不把测试样例做成主页面 |

「服务器内置也可以加」在当前本地产品中可先落实为维护者随版本补充内置规则，不需要新增云端服务。若以后增加规则包下发，只同步规则，检测和原文继续留在本机。

### 实现时不能遗漏的部分

- 普通 API 与 WorkBuddy 原生 HTTPS 目前各自创建 `PrivacyPipeline`。两条入口都必须读取同一套有效规则，不能只让规则编辑器使用新配置。
- 保存规则后，下一条请求应使用新版本；正在处理的请求保持自身规则版本一致。
- 用户正则要有格式校验、运行时间和输入量限制，不能让异常表达式卡死主进程；失败需要明确反馈，不能静默绕过检查。
- 先确认可用规则，再替换当前配置；保存失败不应破坏旧规则。规则值也可能敏感，不写入诊断日志或上传。
- 多规则重叠时需要确定的优先级；请求中存在阻断命中时，不应因另一条替换规则而放行。
- 当前模型认证 Header 由转发层处理，不作为 Prompt 凭据阻断。规则应检查待外发的内容，保留原平台正常认证。

## 7. 语义分类仍是独立缺口

`DisabledSemanticClassifier` 当前为关闭状态并返回空结果；默认策略也没有根据语义结果做决策。存在接口不等于已经具有分类能力。

它应解决的是无法仅靠固定格式判断的内容，例如业务计划、客户资料段落和未公开财务信息。与之相关的人名、地址识别也还需要补齐，但不应把所有能力都笼统算成正则或语义分类。

实现前需要确定类别与独立评测样本，再验证本地推理的误报、漏检、延迟和资源消耗。合格的结果还必须真正接入策略与请求记录。仅在侧栏显示「语义分类」或接上一个空接口不算完成。

建议先完成原生接入、页面精简和规则管理，再开展本地实体识别与语义分类。这是实施顺序调整，没有取消该需求。

## 8. 下一轮顺序与验收条件

| 顺序 | 交付 | 验收条件 |
| --- | --- | --- |
| P0 | WorkBuddy 原生开启 / 停止保护 | 普通 App 启动即可进入流程；沿用原登录和 Auto；授权与重启有明确步骤；真实请求有记录；停止后恢复原网络配置 |
| P0 | 页面精简与真实状态 | 收敛为四个入口；移走开发样例、重复 Local 标签和未实现占位；主要按钮都有实际结果，禁用时说明原因 |
| P1 | 内置 + 自定义规则 | 无需用户先建规则即可检测；支持新增、编辑、启停和本地保存；普通 API 与原生入口均验证生效；错误表达式不会破坏运行 |
| P1 | 真实使用流程回归 | 冷启动、重启、端口冲突、客户端改配置、异常退出、恢复原连接均有验证；测试真实流程，而非只验证按钮存在 |
| P2 | 本地实体识别与语义分类 | 明确类别、独立效果报告、可接受的本地性能、策略实际使用分类结果 |
| 后续主线 | 完整 Agent 与更多原订阅客户端 | 补齐工具循环、流式恢复、会话映射，并逐客户端验收；平台名称和说明页不计入已支持数量 |

双平台安装、签名、公证、开源许可和完整路线仍见 `docs/ROADMAP-REVIEW.md`；其中较早的原生过滤状态是历史快照。此次重点先让一个真实客户端可重复接入、可观察、可恢复，再扩展客户端数量。
